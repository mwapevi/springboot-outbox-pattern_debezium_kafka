# Phase 3: Integrating Apache Kafka

## Overview

The primary objective of this phase was to integrate Apache Kafka into the event-driven MySQL Outbox pattern architecture developed in the previous phases (i.e. Phase 1 andPase 2). Apache Kafka served as the central event streaming platform, which  enabled asynchronous communication between microservices through the exchange of events rather than direct service-to-service interactions.

In traditional synchronous communication,services are tightly coupled, hence requiring one service to wait for another to respond before continuing execution. As the number of services increases, this approach can introduce higher latency, reduce system resilience, and make scaling more challenging. Kafka addresses these limitations by acting as a distributed event broker that decouples event producers from event consumers.

In this implementation, business events generated by the application are published to Kafka topics, where they are stored durably and made available to one or more independent consumers such as Notification and Analytics services. Customer Service producer is only responsible for publishing events to Kafka and is unaware of which downstream services consume them. Likewise, consumers such as Notification and Analytics services subscribe to the topics relevant to them and process events independently at their own pace. This publish-subscribe model enables loose coupling, improved scalability, and greater fault tolerance.

Kafka organizes events into topics, which act as logical channels for different categories of messages. Producers publish events to these topics, while consumers subscribe to receive the events. Kafka persists messages on disk for a configurable retention period, allowing consumers to replay events if necessary.

This phase establishes the messaging infrastructure required for an event-driven architecture, providing a reliable mechanism for exchanging events between distributed services. It also lays the foundation for the subsequent integration of Debezium Change Data Capture (CDC) and the Transactional Outbox Pattern, where Kafka becomes the event streaming platform responsible for delivering database changes to downstream consumers in a scalable and resilient manner.

## Objectives

- Install and configure an Apache Kafka.
- Understand the core concepts of Apache Kafka, including brokers, topics, producers, consumers, and partitions.
- Integrate the Spring Boot application with Apache Kafka using Spring for Apache Kafka.
- Configure Kafka producers to publish business events to Kafka topics.
- Configure Kafka consumers to subscribe to and process events from Kafka topics.
- Establish a scalable messaging infrastructure that serves as the foundation for the subsequent integration of Debezium Change Data Capture (CDC) and the Transactional Outbox Pattern.

### Apache Kafka Installation

This project was implemented using Apache Kafka 3.2.0 running on a Windows environment (localhost).

Download the appropriate Apache Kafka 3.2.0 release from the official Apache Kafka downloads page:

https://kafka.apache.org/community/downloads/

After downloading the archive, extract the contents to a directory of your choice. The project directory structure should resemble the following:

```text
C:\
└── kafka_2.13-3.2.0
    ├── bin
    ├── config
    ├── libs
    ├── licenses
    ├── logs
    └── site-docs
    
```

### Why Apache Kafka 3.2.0?

Apache Kafka 3.2.0 was selected for this project as a stable, well-established Kafka release and to provide practical experience with the traditional ZooKeeper-based Kafka architecture.

The choice also supports the project's learning progression: first understanding the Transactional Outbox Pattern, then introducing Kafka as the event-streaming platform, and finally integrating Debezium CDC.

Kafka 3.2.0 uses ZooKeeper for cluster metadata and controller management. Therefore, in this setup, ZooKeeper is started before the Kafka broker, and Kafka connects to ZooKeeper using:

```properties
zookeeper.connect=localhost:2181

```
of 

```properties
server.properties

```
![server,properties](/docs/artifacts/phase-3/server-properties.png)

**Architectural limitation:**
- Kafka 3.2.0 uses the older ZooKeeper architecture in this setup
- Modern Kafka uses KRaft
- therefore this is a learning/compatibility choice, not a claim that ZooKeeper is the preferred architecture today

### Start Zookeeper

**Open Windows Powershell**

- Navigate to Kafka folder
- Run the command to start Zookeeper
- Keep the terminal open
```command
  cd C:\kafka\kafka_2.12-3.2.0
  bin\windows\zookeeper-server-start.bat config\zookeeper.properties
```
